## 2. 当前已实现能力

### 2.1 账号与访问控制

- 用户名、密码注册登录和登录态恢复。
- 密码哈希、JWT Cookie、来源校验、登录/注册限流和账户安全接口。
- 未登录用户不能操作聊天、好友、农场、邀请币和个人成长数据。
- 用户档案、通知中心、个人主页和好友关系。
- 工位塔防 V1 在浏览器运行，不以登录身份换取游戏奖励。

### 2.2 热点新闻与经验交流

- 热点新闻页面、每日新闻数据、发布日期校验和编辑规则。
- 注册用户聊天室；服务端只保留最近 200 条公开聊天记录。
- 聊天 WebSocket、历史记录和登录鉴权。
- 用户经验交流内容、内容边界和社区规范页面。

### 2.3 统一成长与货币

- 统一等级、经验、体力、办公币、邀请币、背包和不可变资产流水。
- 奖励幂等、防重复领取、事务一致性和 Outbox/Worker 投影。
- 每日任务、签到、最近活动和跨系统可信事件。
- 工位塔防 V1 不读写上述资产，不发放正式办公币、经验或体力。

### 2.4 农场

- 每用户独立土地、服务端成熟时间、种植、收获和作物目录。
- 农场等级和地块数量成长。
- 农场经验、种子、收获奖励与统一办公币循环。
- 简化后的首次游玩流程，降低种植操作复杂度。

详细规则见 `docs/FARM_GAMEPLAY.md`。

### 2.5 《摸鱼升职记》工位塔防 V1（待部署）

- 固定一名“工位守卫”；地图上不会创建第二名玩家角色。
- 角色可用 WASD 或方向键移动，自动攻击范围内敌人，并可用 Space 释放“专注脉冲”。
- 三类办公用品塔：订书机负责单体输出，咖啡机负责减速，打印机负责范围输出。
- 支持在塔位建造、升级和出售，不允许资源变为负数。
- 三波敌人依次为“零散待办”5 只、“催办邮件”7 只、“会议风暴”9 只；最后一只为高生命首领。
- 支持开始下一波、暂停/继续、重新开始和明确的胜负状态。
- 桌面端支持键盘和按钮，移动端提供可触摸操作。
- 只在 `momo.workstation-tower-defense.settings.v1` 保存 `{ bestScore }`；不保存局内资源或可兑换奖励。
- 当前没有服务端存档、排行榜、PVP、离线收菜、升职系统或公司社交。

详细规则和验收口径见 `docs/WORKSTATION_TOWER_DEFENSE_V1.md`。

### 2.6 历史办公室乐斗的退役边界

- `OfficeBattleModule` 已从 `CommunityAppModule` 白名单卸载，当前社区入口不再装配旧 `/api/v1/games/office-battle` 接口。
- 旧模块源码、实体、迁移和 11 张 `office_battle_*` 表原样保留，作为回滚与历史记录；当前产品不再写入。
- 现有角色职业、等级、装备、战报、待领奖励和资产流水不删除、不清零、不改名。
- 已并入统一账户的经验和办公币保持现有余额，不回扣，也不再向塔防重复发放。
- 旧浏览器存档 `zbrs.office-battle.profile.v1` 不读取、不删除、不转换；新存档键与它完全隔离。
- 旧 `/ledou` 和 `/battle` 只用于导向新的工位塔防页面，不恢复旧玩法。

## 3. 工程与部署

- Monorepo：React/Vite 前端、NestJS 后端、共享 TypeScript 包。
- PostgreSQL 保存账号、内容、聊天、农场与现有社区资产；历史乐斗资产只读保留。
- 工位塔防 V1 全部在浏览器内运行，无新服务端 API，无新数据库表。
- Docker Compose 编排 gateway、web、api、migrate、postgres 和 redis。
- 网关提供 HTTPS、反向代理和安全响应头。
- 部署脚本包含环境预检、迁移、健康检查、冒烟检查和备份恢复能力。
- 目标容量按 4,000 注册用户、1,000 人同时在线规划；该目标不等于已通过真实环境压测。

## 4. 发布前验收

1. 执行 `npm ci` 和 `npm run verify`，以本次命令的实际结果作为提交证据。
2. 验证 `/tower-defense` 可进入《摸鱼升职记》，`/ledou` 和 `/battle` 只跳转到该页。
3. 用桌面键盘与手机触控各完成一局，覆盖移动、角色自动攻击、主动技能、三类塔、三波敌人、胜负和重开。
4. 页面与静态资源加载完成后断网，验证当前单局仍可继续，且没有工位塔防 API、办公币、经验、PVP 或排行榜请求。
5. 刷新页面后只恢复本机最高分，不恢复局内金币、敌人、波次或防御塔。
6. 在发布配置中保持 `FEATURE_COMMUNITY_BATTLE_ENABLED=false`，并确认社区应用未装配旧 Office Battle 模块。
7. 先完成数据库备份，再确认旧 `office_battle_*` 表行数和玩家余额在部署前后不变。
8. 通过部署后 HTTP 烟测和实际浏览器验收后，再将本文的“待部署”改为“已上线”。

## 5. 下一阶段建议

1. 为工位塔防设计独立、追加式服务端存档，不改名或复用 `office_battle_*` 表。
2. 服务端能验证每局成绩后再开放排行榜；不直接上传并信任浏览器最高分。
3. 扩展地图、波次、办公用品塔和角色主动技能，并建立确定性数值回归测试。
4. 将“放置离线收菜”、“摸鱼升职”和“公司社交”分别立项；完成服务端权威结算、防作弊和隐私评审前不进入当前 V1。
5. 根据真实并发和静态资源冷启动结果，调整 CDN、API、Redis 和数据库容量。
