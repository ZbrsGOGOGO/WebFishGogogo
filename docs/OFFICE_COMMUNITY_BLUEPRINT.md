# ZBRS 办公室轻社区产品蓝图

> 文档关系：本文保留产品方向和早期蓝图。账号、经验交流、聊天室、农场、邀请、主页、好友等功能的开发与验收，以 [完整产品 PRD v1.0](./PRODUCT_PRD_V1.md) 为准；办公室乐斗的公式、经济和服务端规则，以 [办公室乐斗完整玩法说明 v1.0](./OFFICE_BATTLE_GAMEPLAY_SPEC_V1.md) 为准。发生冲突时，以两份 v1.0 文档为准。

更新时间：2026-08-22

## 1. 产品定位

一句话定位：面向办公室人群的职业主题轻社区；工作时看资讯、交流经验和使用工具，休息时经营工位、投喂好友并完成一场 25～40 秒的办公室乐斗。

核心原则：

- 职业身份贯穿内容、好友、乐斗和成长，但不用于现实职场评价。
- 轻量优先。一次访问必须能在 1 分钟内得到内容、工具结果或一场完整战斗。
- 不做付费概率箱、充值战力、提现和装备交易。
- 匿名试玩进度仅保存在本机；服务端资产只能由服务端规则生成。
- 先完成账户安全、隐私、举报、拉黑和内容审核，再开放真人互动。

## 2. 九系统信息架构

| 系统 | 用户价值 | 首版形态 | 账号要求 |
|---|---|---|---|
| 首页 | 今日总览、快捷入口、成长反馈 | 产品地图 + 乐斗入口 | 否 |
| 热点新闻 | 按职业获取可靠行业资讯 | 后续接自有编辑后台或合规内容源 | 发布前否，个性化需账号 |
| 经验交流 | 分享方法、项目复盘和问答 | 后续建设帖子、收藏、举报、审核 | 是 |
| 农场 | 工位绿植的离线轻养成 | 一键照料、一键收获，减少多步种植 | 是 |
| 乐斗 | 职业构筑、自动观战、装备成长 | 先开放本机 NPC 试玩 | 试玩否，正式资产是 |
| 投喂 | 给好友赠送咖啡、零食和士气 | 每日限次的非交易型社交补给 | 是 |
| 邀请 | 建立真实好友关系和小队 | 邀请码、归因、防刷、奖励上限 | 是 |
| 我的主页 | 职业、装备、荣誉和收藏档案 | 隐私分级的个人档案 | 是 |

第一阶段只让“首页、乐斗、工具箱、小游戏”成为真实入口。新闻、交流、投喂、邀请、主页和好友不制造假内容或空互动页。

## 3. 办公室乐斗的原创边界

目标不是复制另一款游戏后换美术，而是保留抽象体验：挑选对手、战前构筑、自动观战、有限随机、幽默战报、立即成长。

具体表达、数值、职业、技能、装备、交互和经济必须原创。最高人民法院公开案例说明，即使玩法规则本身可借鉴，若整体结构、参数、数值和交互关系高度对应，仍可能构成不正当竞争：<https://www.court.gov.cn/zixun/xiangqing/463511.html>。

公开回顾可确认早期自动战斗产品的核心吸引力来自“玩家负责培养，战斗中负责观看”，而后期系统堆叠和战力膨胀会抬高新人门槛：

- <https://finance.sina.cn/tech/2024-06-05/detail-inaxqxat3097941.d.html>
- <https://www.gamersky.com/news/202503/1891421.shtml>

因此本项目采用“项目攻防”规则：

- 基础属性：活力、执行、抗压、反应、洞察。
- 最多 10 回合；第 8 回合进入“截止日”，行动影响逐回合提高。
- 战斗由固定种子和双方快照决定，可重放、可审计。
- 玩家决策集中在职业、六件装备和后续的三条策略规则。
- 好友战采用异步快照；防守方失败不损失资源。
- 奖励战每日限次，练习战不限次但不产出服务端资产。

## 4. 五职业

| 职业 | 定位 | 专属资源（二期） | 代表行动 |
|---|---|---|---|
| 程序员 | 持续输出、后期成长 | 专注 | 紧急热修、稳定发布 |
| 产品经理 | 节奏控制、改变优先级 | 共识 | 需求冻结、范围重排 |
| 测试 | 防守反击、识别薄弱点 | 证据 | 致命复现、回归锁定 |
| 销售员 | 爆发追击、低状态终结 | 势能 | 临门签单、连续提案 |
| 人力资源管理 | 恢复、净化、持久战 | 士气 | 团队激励、组织协同 |

职业只做约 5%～8% 的软克制，不做不可逆的硬克制。装备和策略应允许玩家改变对局倾向。

## 5. 六装备位

1. 专业工具：职业限定，定义主要行动风格。
2. 工作终端：强化职业机制或改变触发条件。
3. 工牌：提供反应、洞察或开场效果。
4. 职业装：提供活力与抗压。
5. 通勤鞋：提供反应和少量回避类效果。
6. 随身件：补足流派的条件触发效果。

装备等级与稀有度是两个独立维度：

- 等级 1～60：入职、熟练、骨干、资深、专家、首席。
- 稀有度：标准、精工、专业、卓越、代表作。
- 熟练度 +0～+6，强化 100% 成功，不失败、不掉级。
- 同部位强化经验可迁移；重复装备转换为零件，不制造背包垃圾。
- 首版不做套装；二期再增加“稳健、突破、协同、洞察”等工作风格标签。

装备分层只借鉴“等级、稀有度、部位和构筑效果相互独立”的通用设计思想，不复制 DNF 的名称、颜色、数值或套装。Neople 官方文档也将等级与稀有度作为独立数据维度：

- <https://www.dfoneople.com/developers/contents/guide/pages/all>
- <https://www.dfoneople.com/news/notices/4385/Director%27s-Note---March-2025?page=1>

## 7. 服务端领域模型

现有可复用能力：竞技场确定性引擎、双方快照、引擎版本、资产与背包流水、奖励幂等、Outbox、任务和活动投影。

新增模型：

- `battle_class_definitions`：职业基础属性、被动、平衡版本和启用状态。
- `arena_profiles.battle_class_slug`：关联战斗职业；不能复用工具推荐的职业偏好。
- `equipment_definitions`：部位、稀有度、职业限制、属性、效果、等级要求、平衡版本。
- `player_loadout_slots`：`user_id + slot` 唯一，保存六槽穿戴与乐观版本。
- `equipment_instances`：仅在同款多件、随机词条、强化或耐久上线时增加。

战斗快照必须保存：职业、六件装备及属性快照、策略、平衡版本、引擎版本和种子。客户端不得提交胜负、属性、掉落、奖励或随机种子。

最小 API：

- `GET /api/v1/games/office-battle/catalog`
- `GET /api/v1/games/office-battle/bootstrap`
- `PUT /api/v1/games/office-battle/profile/class`
- `GET /api/v1/games/office-battle/equipment`
- `PUT /api/v1/games/office-battle/loadout`
- `POST /api/v1/games/office-battle/battles`
- `GET /api/v1/games/office-battle/battles?cursor=...`

## 8. 上线顺序

### A. 匿名本地试玩

- 九系统产品地图。
- 五职业、六装备位、五档稀有度。
- NPC 自动战斗、逐回合战报、本机进度。
- 不启动 API，不产生可交易或可迁移资产。

### B. 邀请制账号 Beta

- 补齐邮箱规范化、密码规则、验证、找回、注销、停用、会话撤销和条款版本记录。
- 服务端职业、装备、战斗历史和确定性结算。
- 仅 NPC，限制写接口的用户与 IP 速率。
- 本地试玩只迁移职业和界面偏好，不迁移等级、货币或装备。

### C. 好友与简化农场

- 好友、拉黑、举报、隐私范围。
- 异步好友挑战与投喂。
- 农场改为一键种植、一键收获，修复幂等参数校验。

### D. 内容社区

- 自有编辑后台或明确授权的新闻源。
- 经验交流、审核队列、举报、封禁、昵称治理和内容留存策略。
- 最后考虑排行、周榜与公开主页。

## 9. 4000 用户 / 1000 活跃会话边界

匿名试玩仍由浏览器计算，服务器只承担静态资源和 TLS，适合现阶段容量目标。账号 Beta 上线前必须补：

- 真实 PostgreSQL 并发 E2E。
- 乐斗、装备、农场写接口 k6 场景。
- 竞技场只查询未消费且未过期 offer，清理历史 offer。
- 农场相同幂等键必须校验原始地块与作物参数。
- CDN 冷启动验证与静态资源命中率监控。

新闻、社区、好友和投喂必须按读写比例分别压测，不能用当前静态站的 1000 会话模型替代。

## 10. 生产发布合规闸门

本蓝图中的 `/ledou` 当前是本地产品原型，不因 ICP 备案或一般网站审核通过而自动具备公开运营条件。《网络出版服务管理规定》第二十七条规定网络游戏上网出版前需履行审批程序，因此办公室乐斗与现有四款网页游戏都应在再次生产发布前取得出版审批批文，或保存主管部门/专业律师关于具体版本无需另行审批的书面结论：

- <https://www.cac.gov.cn/2016-02/15/c_1118048596.htm>
- <https://www.nppa.gov.cn/bsfw/xksx/tbsm/201512/t20151228_5058.html>

隐私政策也必须在生产发布前配置依法可公开的个人信息处理者名称、真实可用的专用隐私联系渠道、日志保存期限或确定方法，以及查阅、更正、删除和限制处理的申请方式。个人姓名和私人邮箱无需放在首页，但不能让隐私政策只写“联系我们”而没有实际入口。《个人信息保护法》第十七条和《网络数据安全管理条例》第二十一条对此有明确告知要求：

- <https://www.npc.gov.cn/npc/c2/c30834/202108/t20210820_313088.html>
- <https://xzfg.moj.gov.cn/front/law/detail?LawID=1734>

生产预检因此强制要求：`PRIVACY_PROCESSOR_NAME`、`PRIVACY_CONTACT` 和 `PUBLIC_GAME_CLEARANCE_REFERENCE`。任何一项缺失，部署必须失败。本文是工程发布闸门，不替代主管部门或律师的正式意见。
