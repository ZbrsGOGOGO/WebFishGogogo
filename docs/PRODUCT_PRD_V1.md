## 1. 产品定位

ZBRS 是面向办公室人群的职业主题轻社区。用户以明确标注的“乐斗职业”参与内容、养成和社交，而不是接受平台对现实职业的评价。

用户每次访问应在一分钟内完成至少一种价值行为：

- 获取一条来源清楚的资讯；
- 阅读或分享一条实用经验；
- 完成一次好友互动；
- 一键照料工位绿植；
- 完成一场办公室乐斗；
- 使用一个效率工具。

“程序员、产品经理、测试、销售员、人力资源管理”均为游戏角色，不等同于真实职业认证。

## 2. 产品目标、指标与非目标

### 2.1 产品目标

1. 新用户在 3 分钟内完成注册、基础资料和首次有效行为。
2. 建立“内容获取—认识同好—成为好友—投喂/挑战—回访”的闭环。
3. 把农场压缩成每天一次、约十秒完成的轻操作。
4. 让乐斗职业、装备和荣誉成为主页展示内容，但不制造现实身份歧视。
5. 真人互动开放前具备身份核验、举报、拉黑、审核、禁言、封禁和申诉。
6. 所有正式资产、邀请归因、农场成熟时间和战斗结果以服务端为唯一真源。
7. 在 4000 注册用户、1000 同时在线的隔离环境通过容量验收。

### 2.2 北极星指标

**周复合活跃用户数**：一周内完成至少两类有效行为的去重用户数。

有效行为：

- 阅读一篇达到最低停留/滚动条件的经验帖子；
- 发布一条审核通过的帖子或有效回复；
- 完成一次好友互动；
- 完成一次工位绿植照料或收获；
- 完成一场办公室乐斗；
- 完成一次工具操作。

### 2.3 护栏指标

- 举报率、骚扰投诉率、误判率和申诉改判率。
- R0/R1 高风险内容处置时间。
- 资产重复发放数必须为 0。
- 好友拉黑后的跨系统穿透失败数必须为 0。
- 不以消息数量、在线时长、邀请人数或红点点击量单独评价成功。

### 2.4 首版非目标

- 私聊、用户建群和匿名聊天。
- 图片、文件、音视频上传和语音视频通话。
- 通讯录匹配、手机号反查和邮箱反查。
- 好友偷菜、玩家交易、礼物转卖。
- 现金邀请返佣、多级分销或提现。
- 付费概率箱、充值战力、付费体力。
- 直播、弹幕和实时同步 PVP。
- 自动抓取并全文转载第三方新闻。
- 自动生成假用户、假评论、假在线人数或假热度。
- 公开用户真实姓名、手机号、邮箱、精确位置和登录设备。

## 5. 核心用户流程

### 5.1 新用户

访问首页 → 浏览公开内容或匿名试玩乐斗 → Beta 阶段提交准入码 → 注册并验证邮箱 → 设置昵称、预设头像和乐斗职业 → 进入登录后首页 → 完成首次乐斗或首次绿植照料 → 需要发帖、聊天、加好友时完成适用身份核验。

匿名试玩只允许迁移职业和界面偏好，不能迁移等级、装备、货币、胜场和奖励。

### 5.2 内容社交

浏览资讯/经验 → 标记“有用”、收藏或回复 → 查看作者公开主页 → 发送好友申请 → 对方接受 → 投喂或发起异步乐斗。

### 5.3 每日轻量循环

查看通知 → 一键处理工位绿植 → 阅读一条经验 → 给好友一次鼓励 → 完成一场奖励乐斗。

完整日常不能要求用户逐块土地操作、管理多类材料或连续确认弹窗。

## 6. 账号注册、登录与安全

### 6.1 注册需求

| 编号 | 优先级 | 需求 |
|---|---|---|
| ACC-001 | P0 | 支持邮箱、密码、昵称注册；Beta 阶段注册请求必须携带有效 Beta 准入码 |
| ACC-002 | P0 | 邮箱去首尾空格并按统一规则规范化；规范化结果唯一 |
| ACC-003 | P0 | 密码 10～64 字符且 UTF-8 不超过 72 字节；拦截常见弱密码 |
| ACC-004 | P0 | 注册前明确同意服务条款、隐私政策和社区规范 |
| ACC-005 | P0 | 服务端保存条款类型、版本、时间和来源 |
| ACC-006 | P0 | 邮箱验证码一次有效，10 分钟过期，重发有倒计时和日上限 |
| ACC-007 | P0 | 昵称 2～20 字，经过账号信息和内容规则核验 |
| ACC-008 | P0 | 生成随机、不可枚举 publicId，数据库 UUID 不公开 |
| ACC-009 | P0 | 注册、验证码、登录按账号、IP 和风险等级限流 |
| ACC-010 | P0 | 登录、找回密码和验证码重发的公开提示不能泄露账号是否存在 |
| ACC-011 | P0 | 信息发布和即时交流前增加适用的后台真实身份核验 |
| ACC-012 | P0 | 并发注册相同邮箱最多创建一个账号；其余请求返回通用 409，不把数据库错误或既有账号资料暴露给客户端 |
| ACC-013 | P0 | 首版保存“已满 18 周岁”声明的版本、时间和来源；不采集精确生日 |

Beta 注册原子流程：

1. 校验 Beta 准入码，将一个使用名额按规范化邮箱预留 30 分钟。
2. 在同一事务创建 `pending_email` 账号和预留记录，发送 10 分钟有效的邮箱验证码。
3. 邮箱验证成功时原子核销预留名额，将账号切换为 `active`。
4. 预留过期仍未验证时释放名额；账号保留为 `pending_email`，继续验证前必须重新提交有效准入码。
5. 准入码轮换不影响已建立且未过期的预留；仅打开链接、未产生预留的旧码立即失效。

账号生命周期与社交核验分开：

- `accountStatus`：pending_email → active → deleting → deleted；active 还可被 suspended 或 banned，恢复只允许回到 active。
- `socialVerificationStatus`：unverified → pending → verified / rejected / expired。
- `pending_email` 只能验证邮箱或重新提交准入码；不能建立正式资产。
- `deleting` 只允许使用短期恢复会话查看注销影响、撤销注销或退出；普通登录不能恢复完整权限。
- `deleted` 为终态；不得通过状态回写恢复原账号。

身份核验：

- 优先采用移动电话号码等经确认的合规方案。
- 手机号不进入公开主页。
- 如自行保存，使用字段级加密，并用独立 HMAC 索引做唯一性/防刷判断。
- 如接第三方核验，优先只保存核验结果、供应商流水号和最少脱敏信息。
- 第三方回调必须校验签名、时间窗和唯一流水号；浏览器提交的“已核验”结果永不作为真源。
- 上线前由主管部门或专业法律意见确认具体方案。

### 6.2 登录与会话

- 访问令牌建议 15 分钟。
- 刷新会话最长 30 天并滚动轮换。
- 刷新凭据通过 HttpOnly、Secure、SameSite Cookie 保存。
- 长期 JWT 不再写入 localStorage。
- 数据库只保存刷新令牌哈希。
- 检测旧刷新令牌重用时撤销同一令牌族。
- 用户可查看设备、最近活动时间和大致地区，支持单独退出和全部退出。
- 修改密码、注销、停用、封禁或高风险事件立即撤销全部会话。
- Cookie 写接口增加 CSRF 或等效来源保护。
- WebSocket 使用短期身份握手，令牌过期后重新鉴权，不在 URL 中携带长期令牌。

### 6.3 找回密码

1. 用户输入邮箱，页面统一返回“如账号存在将发送邮件”。
2. 一次性链接/验证码 15 分钟失效且只能用一次。
3. 设置新密码。
4. 撤销全部既有会话。
5. 发送不可关闭的安全通知。

### 6.4 注销、停用和封禁

- 用户再次验证密码或验证码后可申请注销。
- 注销前列出资料、内容、好友、农场和乐斗资产影响。
- 进入 7 天冷静期；再次登录可撤销。
- 进入冷静期时撤销普通会话；再次验证凭据后只签发 10 分钟恢复会话，用户明确点击“撤销注销”才恢复 active 和普通会话。
- 期满关闭身份、撤销会话并按数据清单删除或匿名化。
- 争议证据和法定记录隔离保存，不能因注销绕过处置。
- 封禁用户仍可进入只读安全页查看原因并申诉，法律另有要求除外。

| COM-004 | P0 | 支持草稿、预览、发布、编辑、删除和版本记录 |
| COM-005 | P0 | 支持一级评论和一级回复，嵌套不超过两层 |
| COM-006 | P0 | 支持“有用”、收藏和举报；不做踩和公开负分 |
| COM-007 | P0 | 支持最新、热门、未解决和频道筛选 |
| COM-008 | P0 | 问答作者可标记一条已解决回复 |
| COM-009 | P0 | 使用 PostgreSQL 全文检索标题、正文和标签 |
| COM-010 | P0 | 内容有稳定 ID、作者快照、审核状态和版本 |
| COM-011 | P0 | 适用范围内展示 IP 归属地，不展示原始 IP |
| COM-012 | P1 | 支持关注帖子和回复聚合通知 |

首版不开图片、附件和站外链接预览。若允许文本链接，新用户/高风险链接进入人工审核。

### 7.3 内容状态

帖子和评论使用三组正交状态，不能合并成一个字符串：

- `publicationStatus`：draft → pending_review → published。
- `moderationStatus`：normal / limited / hidden。
- `deletedAt`：空值表示存在；有值表示软删除。
- `version`：每次编辑递增，用于乐观并发；问答采纳另存 `acceptedCommentId`。

- 新账号首帖、含链接内容和高风险命中内容先审后发。
- 普通低风险文本可在治理能力允许时先发后巡检。
- limited 仅作者可见并显示原因。
- hidden 对普通用户隐藏但保存证据。
- 作者可将 draft 提交为 pending_review；审核通过后才成为 published。
- 新帖子或评论审核拒绝时记录 `lastReviewDecision=rejected`、原因和审核案件，并退回 draft；作者修改后递增版本，再次提交为 pending_review。
- 作者可主动撤回尚未完成的审核：新内容回到 draft；已发布内容的待审修订标记 withdrawn，线上仍使用上一生效版本。
- 已发布内容重大编辑生成待审新修订，旧修订继续公开；审核通过后原子切换，不短暂暴露未审正文。
- 作者删除只设置 deletedAt；30 天内允许恢复到删除前的发布/审核状态，但不能绕过仍有效的 limited、hidden 或账号处置。
- limited、hidden 和恢复 normal 只能由授权审核角色执行并绑定审核案件。
- 编辑、采纳、删除、恢复均要求 `If-Match`/expectedVersion；版本过旧返回 409。
- 删除、恢复、置顶、关闭评论和审核处置全部写入审计。

### 7.4 冷启动

不制造虚假用户和虚假热度。没有真实内容时只展示：

- 明确标注为平台撰写的使用指南。
- 社区规范和官方示例模板。
- “当前还没有真实帖子”的空状态。

### 8.2 消息需求

| 编号 | 优先级 | 需求 |
|---|---|---|
| CHAT-001 | P0 | 已完成适用身份核验且未禁言的用户才能发言 |
| CHAT-002 | P0 | 单条 1～500 字，纯文本或受限表情 |
| CHAT-003 | P0 | 支持回复、提及、复制、撤回和举报 |
| CHAT-004 | P0 | 用户可在 2 分钟内撤回；版主可隐藏违规消息 |
| CHAT-005 | P0 | clientMessageId 按用户唯一，断线重发不重复 |
| CHAT-006 | P0 | 服务端分配房间递增序号，重连后补齐缺口 |
| CHAT-007 | P0 | 消息风险检查并持久化成功后才 ACK 和广播 |
| CHAT-008 | P0 | 默认 1 条/秒、突发 5 条、60 条/10 分钟 |
| CHAT-009 | P0 | 拉黑在发言、历史读取、回复和提及通知同时生效 |
| CHAT-010 | P0 | 产品可见历史 30 天；安全日志按适用要求另行留存 |
| CHAT-011 | P0 | 只显示近似在线人数，不公开精确最后在线 |
| CHAT-012 | P0 | 断网显示重连中；失败消息不伪装为已送达 |
| CHAT-013 | P0 | 授权运营可把单房间或全站聊天室立即切换为全员只读/紧急关闭 |
| CHAT-014 | P1 | 版主可按房间开启带明确间隔的慢速模式 |

交付语义为至少一次传输，客户端按消息 ID 去重。

拉黑语义：拉黑者不再看到被拉黑者的新消息，历史消息显示占位；双方不能互相回复、提及或产生通知。被拉黑者仍可在公共房间向其他用户发言，单个用户的拉黑不能把对方变成全房禁言。

### 8.3 WebSocket 方案

- 一个页面只建立一个全站 WebSocket。
- 切换房间不重复建立连接。
- 至少两个无状态 API/WebSocket 实例。
- Redis 只负责跨实例广播、在线状态和限流。
- PostgreSQL 是消息、房间序号和审核状态真源。
- 数据库提交后才 ACK 和广播。
- 多实例乱序时客户端按服务端序号排序，并通过 REST 补缺。
- 在线状态 20 秒心跳、45 秒 TTL，不写数据库。
- Redis 故障时聊天室降级为只读/重连，不拖垮账号、帖子、农场和乐斗。
- 消息正文不得写入普通错误日志。

最小事件契约：

| 方向 | 事件 | 用途 |
|---|---|---|
| 客户端 → 服务端 | chat.subscribe | 订阅固定房间并提交最后收到的房间序号 |
| 客户端 → 服务端 | chat.unsubscribe | 取消房间订阅 |
| 客户端 → 服务端 | chat.send | 提交 roomSlug、clientMessageId 和正文 |
| 客户端 → 服务端 | chat.withdraw | 在允许时间内撤回本人消息 |
| 服务端 → 客户端 | chat.ready | 返回当前序号和是否需要 REST 补缺 |
| 服务端 → 客户端 | chat.ack | 返回 clientMessageId、正式消息 ID 和房间序号 |
| 服务端 → 客户端 | chat.message.created | 广播已持久化且允许展示的消息 |
| 服务端 → 客户端 | chat.message.updated | 广播撤回、隐藏或恢复状态，不重新下发被隐藏正文 |
| 服务端 → 客户端 | chat.error | 返回稳定错误码、是否可重试和 retryAfter |

所有客户端事件带协议版本和请求 ID；未知事件、越权房间和超限载荷直接拒绝，不做宽松解析。

`chat.send` 载荷固定包含 `protocolVersion`、`requestId`、`roomSlug`、`clientMessageId`、`body`，可选 `replyToMessageId` 和最多 5 个 `mentionPublicIds`。服务端从正文与显式名单交叉验证提及，不能仅凭客户端名单生成通知。

首版稳定错误码至少包括：`AUTH_REQUIRED`、`SOCIAL_VERIFICATION_REQUIRED`、`ROOM_READ_ONLY`、`ROOM_CLOSED`、`MUTED`、`RATE_LIMITED`、`MESSAGE_TOO_LONG`、`REPLY_NOT_FOUND`、`MENTION_NOT_ALLOWED`、`CONTENT_REJECTED`、`SEQUENCE_GAP` 和 `INTERNAL_RETRYABLE`。

### 8.4 运营前置条件

## 9. 简化农场：工位绿植

### 9.1 产品决定

旧版多地块、种子、水、阳光、肥料和逐块收获不进入新首版。主界面改成一株“工位绿植”和一个主按钮。

不再要求用户理解：

- 土地数量和地块选择。
- 种子背包。
- 多种资源余额。
- 逐块浇水和收获。
- 虫害、天气、偷菜和概率失败。

### 9.2 状态机

idle → 一键照料 → growing → 服务端成熟 → ready → 收获并继续照料 → 自动开始下一周期

### 9.3 规则

| 编号 | 优先级 | 需求 |
|---|---|---|
| FARM-001 | P0 | 首次进入只展示默认绿植和一个主按钮 |
| FARM-002 | P0 | 主按钮自动完成开始、收获或收获并续种 |
| FARM-003 | P0 | 首次周期 30 秒，标准周期 20 小时 |
| FARM-004 | P0 | 成熟时间以服务端为准，离线继续 |
| FARM-005 | P0 | 所有操作带幂等键，不能重复收获 |
| FARM-006 | P0 | 奖励固定透明，每个业务日最多一次标准奖励；业务日按 Asia/Shanghai 05:00 切换 |
| FARM-007 | P0 | 标准奖励建议 20 全站 EXP、5 办公币和 10 绿植经验 |
| FARM-008 | P0 | 首次收获额外 40 绿植经验，立即解锁第二种外观 |
| FARM-009 | P0 | 农场等级只解锁植物、花盆和主页展示，不直接增加乐斗胜率 |
| FARM-010 | P0 | 好友投喂只显示鼓励动画，不代收、不偷取资产 |
| FARM-011 | P1 | 首页可直接完成主操作，无需进入农场页 |
| FARM-012 | P1 | 用户可选择下一周期外观，不选则自动延续 |

20 小时周期只提供登录时间弹性，不增加日奖励次数：

- 每次成熟后点击都成功收获并自动开始下一周期。
- 当业务日标准奖励尚未领取时，发放 FARM-007；首次收获同时发 FARM-008 新人加成，并把当天标准奖励记为已领。
- 同一业务日再次收获只播放成长反馈并启动下一周期，不再发全站经验、办公币或绿植经验；按钮旁提前显示“今日奖励已领取”。
- 标准奖励凭证使用唯一键 `(userId, serviceDate, STANDARD)`；新人加成使用用户唯一凭证 `(userId, ONBOARDING)`。
- 某业务日领取标准奖励即记为一次连续照料；与上一业务日相邻则加一，漏掉整个业务日则下次从 1 开始。连续天数只解锁外观，不加战斗属性。

### 9.4 迁移

- 当前未公开的测试农场数据默认不迁移。
- 如果上线前已存在真实资产，按旧农场等级和收获次数转换为确定性外观/办公币补偿。
- 旧种子、水和肥料不能直接变成可交易资产。
- 上线迁移前生成影响用户清单并演练回滚。

### 9.5 验收

- 15 秒内看懂唯一主操作。
- 从进入到完成照料最多两次点击。
- 并发重复点击只创建一个周期和一笔奖励。
- 跨设备和修改客户端时间不能提前成熟。
- 360px 宽手机可以无横向滚动完成主流程。

## 10. 邀请系统

### 10.1 两阶段用途

- Beta 准入码 `beta_access_code`：只承担注册名额控制，由管理员生成，不归属于普通用户，不发奖励。
- 推荐码 `referral_code`：防刷稳定后才开放，用于记录邀请关系并发固定、封顶、非现金奖励，不能作为 Beta 准入码混用。

两类代码均有明确 `purpose`，数据库、接口、页面文案和统计完全分开。

### 10.2 流程

Beta 准入：管理员生成单次或定额准入码 → 用户提交准入码和注册资料 → 预留名额 → 邮箱验证 → 原子核销并激活账号。

推荐奖励：已激活用户生成推荐链接/推荐码 → 新用户访问并在注册时绑定 → 注册并验证 → 达到有效用户里程碑 → 双方获得固定奖励。

有效里程碑：

- 邮箱和适用身份核验完成。
- 账号存续满 72 小时。
- 至少两个不同自然日完成有效行为。
- 未命中多账号、批量注册或异常关系风险。

### 10.3 需求

- 两类代码均使用至少 128 位随机值，服务端只保存安全摘要、purpose、额度、状态和到期时间。
- 落地页收到原始代码后立即换成短期、同站绑定凭证并从地址栏移除；访问日志、分析事件和 Referrer 不记录原始代码，预览接口使用请求体并返回 `no-store`。
- 首批 100 个名额由管理员后台生成默认单次 Beta 准入码；批量码必须设置总额度、到期时间和用途，并记录操作者。
- 每名已激活用户最多有一个有效推荐码，可主动轮换；旧码失效，但既有绑定关系不变。
- 被邀请用户最多绑定一次，核验后不能换邀请人。
- Beta 名额按第 6.1 节在邮箱验证时核销；推荐关系在创建账号时绑定，奖励只在有效里程碑通过后发放。
- 代码预留、账号创建、核销/绑定和使用次数分别在对应同一事务内完成，不以页面打开次数扣额度。
- 页面显示已打开、已注册、待达标、已达标、无效。
- 不展示被邀请人的邮箱和手机号。
- 每日最多 5 名、每月最多 20 名有效邀请；运营可降低。
- 奖励建议双方各 30 办公币和一个无属性徽章，每月最多 5 次奖励。
- 不做现金、提现、多级分成和稀有装备奖励。
- 同手机号、异常 IP 聚集、短时批量账号或封禁关联账号不发奖。
- 不为邀请建立侵入式跨站指纹。
- 风险审核和人工改判有申诉及审计。
- 奖励使用唯一来源凭证，重复回调不重复发放。

1. 安全或违规处置通知。
2. 好友申请和回复。
3. 绿植主操作。
4. 乐斗奖励额度。
5. 投喂和好友挑战。
6. 关注帖更新。
7. 职业相关资讯。
8. 工具入口。

每张卡片只有一个主要动作，不复制完整子系统。

### 14.3 热点新闻

- 只接自有编辑后台、官方来源或明确授权内容源。
- 保存来源、标题、发布时间、原文链接和授权状态。
- 未确认许可前不自行采编新闻、不全文镜像。
- 新闻评论首版关闭，讨论跳转经验交流并携带来源链接。
- 排序结合时效、来源可信度、用户偏好和负反馈，不只看点击量。
- 个性化推荐提供关闭选项和非个性化列表。

### 14.4 乐斗

- 匿名资产不迁移为服务端资产。
- 正式等级、装备、奖励和战绩全部服务端结算。
- 好友主页可发起异步挑战；防守失败不扣资源。
- 每日奖励战有限，练习战无限但不产出。
- 投喂不改变战斗属性。
- 乐斗结算通过 Outbox 投影通知、任务和主页活动。

完整规则见 [办公室乐斗完整玩法说明](./OFFICE_BATTLE_GAMEPLAY_SPEC_V1.md)。

## 15. 通知中心

通知分类：

- 账号安全和系统公告。
- 回复、提及和审核结果。
- 好友申请。
- 投喂。
- 邀请达标。
- 绿植成熟。
- 乐斗挑战和结果。

要求：

- 数据库持久化；WebSocket 只负责实时提示。
- 载荷保存资源 ID 和必要快照，不复制完整帖子/聊天正文。
- 同一业务事件用唯一键去重。
- 支持单条已读、分类全读和全部已读。
- 红点封顶 99+。
- 普通聊天消息不逐条生成通知，只通知回复、提及和公告。
- 同一帖子短期多次回复聚合。
- 安全、条款和违规处置通知不可完全关闭。
- 普通通知默认展示 90 天，法定审计记录另存。

### 20.2 风险分级

| 等级 | 示例 | 默认动作 |
|---|---|---|
| R0 | 明显违法、严重人身安全风险、重大泄露 | 立即阻断、冻结传播、保存证据并升级 |

- 按风险、时间、对象和举报量筛选。

- 隐藏、恢复、限流、禁言和封禁。
- 强制填写原因和期限。
- 自动生成用户通知。
- 支持申诉复核。
- 高风险管理员操作双人审批。
- 所有操作全量审计。

- 聊天产品可见历史：30 天。
- 普通通知：90 天。

## 22. 技术架构

4000 用户不需要拆微服务。保持 NestJS 模块化单体：

```text
CDN / Nginx
├─ React 静态资源
├─ API + WebSocket 实例 × 2
├─ Worker × 1～2
├─ Redis
└─ 独立 PostgreSQL
```

边界：

- PostgreSQL 是账号、关系、内容、消息、农场和游戏资产唯一真源。
- Redis 只做缓存、分布式限流、在线状态和跨实例广播。
- Outbox 负责通知、活动、任务和审核异步投影。
- 首版无用户上传，不需为社区内容增加对象存储。
- 静态资源放 CDN，API 无状态并至少两实例。
- 新增社区部署白名单，/api 只暴露已完成模块。

## 23. 非功能需求

### 23.1 容量数据

容量定义：

- 4000 表示隔离环境中的已激活注册账号数据基数，不是单日访问量。
- 1000 表示同一时刻持续活跃的独立浏览器会话；容量测试中每个合成账号只建立一个会话。
- 每个浏览器会话最多建立一个全站 WebSocket，因此 1000 会话包含最多 1000 条 WebSocket，不是在 1000 在线之外再增加 1000 人。
- 现有 `CAPACITY_4000_USERS.md` 和 `loadtest/k6/capacity.mjs` 只覆盖静态公开版/只读 API。社区功能上线前必须新增独立混合写请求与 WebSocket 脚本，本节口径取代旧静态版口径。

隔离环境至少准备：

- 4000 个合成账号和档案。
- 1000 个独立会话。
- 2 万条好友关系/申请。
- 1 万次邀请核销。
- 100 万条聊天消息。
- 4000 个工位绿植。
- 10 万场乐斗和足量装备。

### 23.2 性能门槛

| 指标 | 门槛 |
|---|---|
| 公开/普通读取 | p95 < 500ms，p99 < 1000ms |
| 已登录复杂读取 | p95 < 800ms，p99 < 1500ms |
| 普通写入 | p95 < 1000ms |
| HTTP 失败率 | < 1% |
| WebSocket 握手成功率 | > 99.5% |
| 聊天持久化 ACK | p95 < 500ms，p99 < 1500ms |
| 同地域广播 | p95 < 1000ms，p99 < 2000ms |
| 消息重复展示 | 0 |
| ACK 后消息丢失 | 0 |
| 资产重复发放 | 0 |
| 数据库连接池 | 稳态 < 70% |
| CPU / 内存 | 稳态 < 70% / < 75% |
| Outbox 最老事件 | 正常 < 60 秒 |

### 23.3 压测

1. HTTP 稳态 400 RPS × 10 分钟。
2. HTTP 峰值 800 RPS × 5 分钟。
3. WebSocket 升至 1000 连接并保持 30 分钟。
4. 1000 WebSocket + 400 HTTP RPS + 20 消息/秒。
5. 峰值 1000 WebSocket + 800 HTTP RPS + 100 消息/秒。
6. 30% 连接在 30 秒内重连。
7. 杀掉一个实例，95% 断线用户 10 秒内重连。
8. 至少 2 小时 soak；聊天室另做 8 小时内存检查。

组合场景的 HTTP 权重固定为：公开首页/资讯/帖子读取 35%，已登录主页/好友/通知/聊天历史读取 35%，账号以外的普通业务写入 20%，登录刷新与安全接口 5%，乐斗开战和结算读取 5%。聊天发送走 WebSocket，不重复计入 HTTP RPS。

1000 条 WebSocket 中，100 条只接收全站通知，300 条订阅综合大厅，其余五个职业房间各 120 条。稳态聊天输入 20 条/秒保持 30 分钟；峰值 100 条/秒保持 5 分钟。服务端必须按实际房间订阅者完成广播，不能用无订阅空消息代替扇出测试。

HTTP 稳态、峰值、在线和组合场景均连续通过 3 次。

### 23.4 可用性与恢复

- 月度可用性目标 99.9%，计划维护除外。
- RPO ≤ 15 分钟，RTO ≤ 2 小时。
- PostgreSQL 使用 PITR/WAL 或满足目标的托管备份。
- 必须实际恢复演练。
- Redis 丢失不能造成资产、好友和已 ACK 消息丢失。
- 发布保留上一镜像和可验证回滚。

### 23.5 可观测性

- 全链路请求/事件 ID。
- 结构化日志和敏感字段脱敏。
- API 路由延迟、错误和限流。
- WebSocket 连接、重连、ACK、广播和丢弃。
- Redis 连接、内存和 Pub/Sub 错误。
- PostgreSQL 连接、锁、慢查询、WAL 和磁盘。
- Worker 积压、重试和死信。
- 审核积压和最老案件。
- 告警负责人和处理手册。

日志不得写密码、验证码、刷新令牌、完整邮箱/手机号或聊天正文。

## 25. 分阶段上线

### 阶段 0：治理和发布闸门

- 业务主体、隐私渠道和数据清单。
- 社区规范、账号规则和申诉。
- 身份核验方案。
- 新闻来源与授权边界。
- 游戏发布资质/书面结论。
- 审核台、举报和审计。
- 备份恢复、监控和值班。

### 阶段 1：100 人邀请制账号 Beta

- 规模指已激活累计账号不超过 100，目标并发会话 30。
- 安全重构、邮箱验证、邀请准入。
- 会话/设备、注销、通知。
- 私有主页和身份核验。
- 不开放帖子和聊天。

退出：注册、找回、撤销、注销和管理员停用全部验收，无未解决 P0/P1 安全问题。

### 阶段 2：300～500 人

- 规模指已激活累计账号 300～500，目标并发会话 150。
- 好友、拉黑、举报。
- 投喂。
- 无奖励邀请归因。
- 一键工位绿植。
- 服务端 NPC 乐斗。
- 好友可见主页。

退出：无重复关系、投喂、照料、奖励；拉黑跨系统即时生效。

### 阶段 3：1000 人以内

- 规模指已激活累计账号不超过 1000，目标并发会话 300。
- 帖子、评论、收藏和搜索。
- 审核、举报和申诉。
- 固定频道和新闻跳讨论。

退出：内容可阻断、隐藏、恢复；审核台和版主值班稳定。

### 阶段 4：聊天室

连接数在同阶段现有账号中按 50 → 200 → 500 → 1000 放量，不额外增加同等人数。每档覆盖完整高峰，并检查消息延迟、重连、审核积压和版主负荷。

### 阶段 5：4000 用户

- 全量容量场景连续通过 3 次。
- 恢复演练通过。
- 社区治理 SLA 达标。
- 未解决 P0/P1 为 0。
- 新闻、游戏、账号和个人信息发布闸门确认。

## 26. 总体验收标准

### 26.1 功能

- 未登录不能调用认证写接口。
- 未完成适用核验不能发帖、评论或聊天。
- 注册、登录、找回、设备退出和注销完整。
- 好友、拉黑、邀请、投喂和绿植并发无重复。
- 用户可控制主页字段可见性。
- 内容可发布、审核、举报、隐藏、恢复和申诉。
- 聊天断线补缺且不重复。
- 工位绿植主操作最多两次点击。
- 好友挑战不扣防守方资产。
- 本机乐斗资产不能进入服务端。

### 26.2 安全与治理

- 所有关键入口独立限流。
- 长期会话不存 localStorage。
- 密码、身份标识和刷新令牌不明文保存。
- 拉黑在帖子提及、聊天、好友、投喂和乐斗全部生效。
- 版主/管理员操作全量审计。
- 举报和申诉入口清晰。
- 隐私政策与实际处理、留存和权利渠道一致。

### 26.3 体验

- 360px 宽手机完成全部主流程。
- 键盘完成注册、发帖、好友和照料。
- 表单错误定位具体字段并保留输入。
- 异步操作都有加载、成功、失败和重试。
- 空社区显示真实空状态。
- 首页每卡只有一个主要操作。

### 26.4 运维

- 4000 合成用户、1000 在线和 1000 WebSocket 验收通过。
- CPU、内存、连接池和 Worker 符合门槛。
- Redis 故障时除实时聊天外核心模块继续。
- 数据恢复后好友、资产、邀请、消息和审核一致。
- 发布、回滚、备份和恢复均有记录。
